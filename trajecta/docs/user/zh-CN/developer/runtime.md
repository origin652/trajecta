# 输出与运行时

运行时在一次 `trajecta-core` 模拟外层提供持久化本地任务控制。它接收已经验证的请求，预留主机
资源，启动独立工作进程，记录进度，并在结束时协调结果状态。工作进程使用的数值运行器与核心
直接测试中的运行器相同。

这一设计中有两个 SQLite 数据库：

| 数据库 | 维护者 | 用途 |
| --- | --- | --- |
| 本地任务数据库 | `trajecta-job` | 队列状态、资源预留、工作进程租约、事件、执行轮次和验证历史 |
| 执行轮次目录中的 `particles.sqlite` | `trajecta-core` | 粒子、质量、事件、状态和终止等科学结果 |

两个数据库有各自的结构定义与生命周期。读取任务状态无需打开科学结果；守护进程停止后，结果
检查仍可独立进行。

## 请求入队

`trajecta-cli` 将 `run` 参数转换为 `SubmitRequest`。输入可以是已定稿项目加其中登记的运行配置，
也可以是显式的解析后的案例与运行配置。请求还包含：

- 从本地资源池预留的 CPU 槽位；
- 以 MiB 表示的内存预留；
- 工作线程数量，其值不能超过 CPU 预留。

守护进程先根据配置容量验证请求，再写入任务数据库。入队会创建两个 UUIDv7 标识：

| 标识 | 生命周期 |
| --- | --- |
| 任务系列 ID | 连接首次提交和后续所有重跑 |
| 运行 ID | 标识一个不可变执行轮次及其输出目录 |

执行轮次编号从 1 开始，并在系列内递增。重跑会把已经验证的输入和资源请求复制到新建的排队
轮次，不会复用或覆盖早期目录。

## 持久化状态机

调度器可见状态如下：

```text
queued -> starting -> running -> complete
                         |       completed_with_particle_errors
                         |       failed
                         |       interrupted
                         +-> cancelling -> cancelled
```

`starting` 覆盖资源预留和进程启动。`cancelling` 表示协作式取消请求已经记录，工作进程正在
等待安全宏步边界。终态不再转换，恢复过程也不会再次派发。

所有转换都通过任务数据库事务应用。一次转换涉及状态行、资源预留、工作进程
租约、诊断和持久化事件时，这些内容会在同一个任务数据库操作内更新。非法状态
边会返回带具体类型的任务存储错误。

## 任务数据库存储

`LocalJobCatalog` 使用 SQLite，启用外键与 WAL，锁等待超时为 5 秒。守护进程管理的队列
变更采用完整同步持久化。工作进程遥测使用独立连接和普通同步模式，因为心跳与进度样本属于
辅助信息；执行轮次状态转换仍由守护进程连接
完成。

任务数据库记录以下内容：

- 每个执行轮次的当前快照；
- 资源请求与输出目录分配；
- 守护进程和工作进程租约；
- 序号单调递增、可供多个读者同时读取的事件；
- 成功执行轮次的完整验证摘要；
- 各次重跑之间的替代关系；
- `job forget` 产生的可见性变化。

读取事件不会消费行。两个读取端可以请求相同的序号范围，`job events --follow` 也会从各自
的游标继续。因此终端用户、监控进程和 AI 助手可以同时观察同一任务，不会争抢消息。

## 调度器与资源池

`plan_dispatch` 是纯调度函数。输入包括配置的资源容量、当前活动预留、持久化 FIFO 队列和
外部内存压力标记；输出包括选中的运行 ID，以及需要由任务数据库原子保存的队首绕过计数。

通常按 FIFO 调度。队首请求暂时无法放入剩余 CPU 或内存池时，较小的后续请求可以利用空闲容量。
同一个受阻的队首请求最多被绕过三次。达到上限后，调度器会为它保留后续资源，并停止选择
更靠后的任务。

外部内存压力处于活跃状态时，派发会暂停。超过守护进程总容量的请求在提交阶段就会
被拒绝，因此永远无法执行的任务不会长期占据队首。

调度器管理声明的预留。任务入队后，操作系统中的其他进程仍可能继续占用内存。这类
情况由工作进程终止与恢复处理；资源模型不会试图控制主机上的其他程序。

## 守护进程所有权与本地 IPC

同一时刻只有一个守护进程拥有任务数据库。租约包含实例 ID、PID、进程启动标记和心跳。
启动标记用于区分原进程与之后复用同一个数字 PID 的其他进程。

CLI 客户端通过本地 IPC 与同一发布的守护进程通信。请求和响应由
`trajecta-job::ipc` 定义类型，单个消息帧上限为 4 MiB。任务事件保留在任务数据库中，因此 IPC
负责发起查询，不承担临时事件队列。

守护进程的每轮派发循环都不会长期阻塞：

1. 读取排队中执行轮次与活跃预留。
2. 计算一份派发计划。
3. 将选中的任务转换为 `starting`，同时保存队首绕过计数。
4. 以隐藏的 `__worker` 模式启动当前可执行文件。
5. 核对进程 ID 与启动标记，并附加工作进程租约。
6. 启动失败或租约附加失败时，写入受控终态及诊断。

Windows 启动工作进程时不会显示额外控制台窗口，Ubuntu 使用独立子进程。前台与后台
CLI 模式的差别在于客户端是否等待；两者都提交到相同守护进程，执行轮次结构也一致。

## 工作进程执行

工作进程接收一个运行 ID，并重新打开任务数据库。开始科学计算前，它会确认租约与启动标记和
执行轮次匹配。随后按以下顺序工作：

1. 重新加载并验证解析后的项目输入。
2. 为已经分配的执行轮次构造生产 `SimulationRunner`。
3. 将任务数据库状态转换为 `running`。
4. 通过 `trajecta-core` 执行宏步。
5. 按限定的采样间隔报告心跳和进度。
6. 关闭输出产物，并将运行清单终态返回任务数据库。

进度包括已完成宏步数、模拟时间、活动粒子数，以及正常与异常终止总数。资源观测已经为实际
运行时间、CPU 时间和 RSS 定义持久化结构；没有采样的字段保持缺省，不会填入估算值。

工作进程适配层不包含另一套科学算法。它负责解析文档、提供运行器控制，并将 `RunOutcome`
映射到任务数据库。

## 科学输出事务

执行轮次目录会包含运行中清单、`particles.sqlite`、临时溯源记录文件、工作进程日志，以及
需要保留的诊断材料。SQLite 写入端采用[结果与 SQLite 参考](../reference/results-sqlite.md)
中的版本化结构定义。

运行期间遵循以下规则：

- 外键始终启用；
- 输出事件定义物理采样时间；
- 粒子先于对应质量和状态写入；
- 生命周期事件使用有界事务；
- 普通计划执行的输出会提交事务；
- SQLite 保持 WAL 模式，使已索引读取器能读取高水位快照，同时不阻塞写入器。

正常收尾的顺序如下：

1. 提交待写 SQLite 行，并更新终态运行行。
2. 执行 `PRAGMA wal_checkpoint(TRUNCATE)`，要求终态 WAL 为空。
3. 检查结构定义 pragma 和 `PRAGMA integrity_check`。
4. 统计全部公开表，并计算规范 SQL 摘要。
5. 关闭写入器连接，计算独立 SQLite 数据库的散列。
6. 从排序后的临时记录流写出溯源信息文件，同时与 SQLite 样本游标对照。
7. 验证临时包，原子重命名，再计算内容摘要与规范输出摘要。
8. 将行数、终止摘要、质量账本、SQLite 文件散列和溯源记录摘要加入
   终态运行清单。
9. 通过同目录临时文件、`sync_all` 和原子重命名写入运行清单。

终态运行清单是最后完成的绑定记录。状态为 `complete` 时，它引用的产物已经关闭，文件散列和
规范化摘要也已确定。

溯源信息或 SQLite 收尾失败时，运行器会中止或隔离受影响的输出；若仍能安全收尾，则写入
`failed` 运行清单。临时文件和中断诊断文件用途不同：成功结束后会删除排序过程中产生的临时
文件，中断时留下的诊断材料则继续保留。

## 取消

安全取消和强制取消会留下不同状态的结果。

### 安全取消

守护进程把安全取消请求写入工作进程租约。`CatalogRunnerControl` 在下一次采样的宏步
边界向运行器返回 `Cancel`。运行器按正常流程关闭部分输出，写入 `cancelled` 运行清单，任务数据库
再接收该终态。

!!! tip "安全取消不生成续跑检查点"

    `job rerun` 会从解析后的输入创建新执行轮次。

### 强制取消

守护进程会同时验证 PID 和进程启动标记，然后停止工作进程。之后检查执行轮次：

- 工作进程如果刚好在终止操作的竞态窗口内完成终态运行清单，任务数据库会接收已经验证的终态；
- 其余情况将执行轮次标为 `interrupted`，并保留中断诊断文件。

排队任务可以在工作进程启动前取消。对终态执行轮次重复取消不会重新打开该执行轮次。

## 重启与异常恢复

守护进程重启后，恢复会比较持久化租约、操作系统进程标识和执行轮次运行清单。每个活跃
执行轮次会得到一种处理结果：

| 观察到的状态 | 恢复动作 |
| --- | --- |
| 工作进程 PID 与启动标记仍然存活 | 将租约重新附加到新的守护进程实例 |
| 已经存在有效终态运行清单 | 将该状态协调到任务数据库 |
| 没有匹配的活动工作进程，也没有有效终态结果 | 将执行轮次标为中断，并保留目录 |

进程启动标记可以避免把复用 PID 的无关进程当成 Trajecta 工作进程。执行轮次转入终态
状态后，恢复还会释放 CPU 与内存预留，使队列中的任务可以继续。

已完成的执行轮次保持不可变。守护进程重启、客户端重启或新的任务提交都不会使它
重跑。只有显式 `job rerun` 会创建另一个执行轮次。

## 执行轮次历史与清理计划

历史按执行轮次编号升序保留全部执行轮次。完整执行轮次通过完整验证后，可以记录
规范化输出摘要。同一个系列中出现较新的、通过完整验证的执行轮次时，历史可以把早期执行轮次
标为已替代，同时保留原文件。

`job forget` 只改变任务在日常列表中的可见性，不会删除执行轮次目录。当前的 `job prune`
只返回顺序固定的清理预览，列出以后可以清理的路径；`0.1.0-alpha.1` 不提供应用该计划的参数。

## 运行时修改检查表

| 范围 | 需要增加或重跑的检查 |
| --- | --- |
| 状态转换 | 合法与非法转换、事件顺序、资源释放 |
| 任务数据库结构 | 全新创建、重新打开、WAL、并发读取、格式版本拒绝 |
| 调度器 | FIFO、最多三次绕过、容量超限、外部内存压力 |
| IPC 消息 | 编解码往返、帧大小上限、同版本客户端与服务端 |
| 工作进程启动 | PID 标记探测、启动失败、租约附加竞态、保留日志 |
| 安全取消 | 宏步轮询、`cancelled` 运行清单、末尾事件、部分结果验证 |
| 强制取消 | PID 复用防护、终态竞态协调、中断诊断保留 |
| 输出写入端 | 事务回滚、表行数、读取器快照、终态检查点 |
| 运行清单或溯源信息 | 原子替换、标识不一致、失败产物隔离、完整验证 |
| 重跑与历史 | 新运行 ID、递增执行轮次、保留已完成轮次、清理预览 |

运行时集成测试应启动生产守护进程与工作进程可执行文件。测试用进程管理器适合构造罕见的启动
和恢复竞态，端到端测试则确认适配层最终调用真实运行器。
