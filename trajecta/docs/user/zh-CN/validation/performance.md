# 性能测量方法

公开基准分别测量数值输送和完整结果生成。Trajecta 的默认结果还包括可查询的粒子历史数据库、
生命周期收尾、字段溯源及后续验证所需信息，因此输送时间与用户等待完整结果的时间回答的是两个
不同问题。

## 基准环境

| 项目 | 固定取值 |
| --- | --- |
| 操作系统 | WSL2 中的 Ubuntu 24.04.1 LTS |
| 架构 | x86_64 |
| 测试时的 CPU 绑定 | 逻辑 CPU `0-3` |
| 工作线程 | 4 |
| 气象资料 | 已对齐的 ERA5 混合模式层案例 |
| 模拟时长 | 3,600 秒 |
| 输送步长 | 600 秒 |
| 结果输出间隔 | 1,200 秒 |
| 粒子数 | 10,000 和 50,000 |
| 预热 | 每种模式、每种粒子数各运行一次 |
| 计时样本 | 每种模式、每种粒子数各运行三次 |

三次计时运行采用轮换顺序。10,000 粒子下，三种模式分别在一轮中首先运行；50,000 粒子重复同样
轮换。这样可以把首次运行、文件缓存和相邻进程影响分散到各模式。

## 两类计时边界

基准独立运行三种模式：

| 模式 | 计时内容 | 生成产品 |
| --- | --- | --- |
| FLEXPART 核心 | 以输送为主的执行路径，尽量减少比较输出 | 核心运行状态和计时记录 |
| FLEXPART 完整输出 | 输送及粒子 NetCDF 写出 | 一个粒子 NetCDF 与运行记录 |
| Trajecta 完整输出 | 输送、结果写出和正常收尾 | 运行清单、SQLite、溯源信息及验证输入 |

### 等效核心

Trajecta 在生产运行器中记录各阶段时间。等效核心定义为：

```text
runner_total - runner_output
```

该范围包含气象查询、粒子群处理、积分和边界计算，扣除已测量的输出阶段。它与 FLEXPART 核心
时间比较。正式比值为：

```text
Trajecta 等效核心中位数 / FLEXPART 核心中位数
```

固定接受上限为 `1.5`，两个粒子规模的比值都低于该值。

### 完整产品

完整产品时间沿各程序的常规输出路径测量。FLEXPART 写入粒子 NetCDF；Trajecta 写入带索引的
SQLite 粒子历史，并完成运行清单和字段溯源收尾。表格将两者并列显示，不对完整产品套用核心
比值上限。

!!! tip "先确定要比较哪段时间"

    比较输送计算时使用等效核心；估算一次完整运行需要等待多久时使用完整产品。

## 样本如何汇总

预热运行先建立代码和资料访问路径，不进入公开中位数。对每种正式模式和粒子数：

1. 运行器可用时以纳秒精度记录墙钟时间，同时在进程外使用 `/usr/bin/time -v`；
2. 保留峰值常驻内存、用户 CPU 时间、系统 CPU 时间和文件系统计数；
3. 将三次墙钟样本排序；
4. 取中间一项作为中位数；
5. 用“粒子数 ÷ 中位秒数”计算吞吐。

原始 CSV 包含所有预热与正式样本。例如，50,000 粒子的 FLEXPART 核心三次正式运行分别为
2.87、1.31 和 1.34 秒，因此公开中位数为 1.34 秒。

## 中位墙钟时间

| 粒子数 | FLEXPART 核心 | Trajecta 等效核心 | 核心比值 | FLEXPART 产品 | Trajecta 产品 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 1.330 s | 0.465 s | 0.350 | 1.310 s | 2.195 s |
| 50,000 | 1.340 s | 1.469 s | 1.097 | 1.370 s | 8.680 s |

10,000 粒子时，Trajecta 的输送范围短于 FLEXPART 核心中位时间。50,000 粒子时，两条核心路径
接近，Trajecta 约为 FLEXPART 的 1.10 倍。

Trajecta 完整产品随粒子数增长得更明显。50,000 粒子下，等效核心为 1.469 秒，完整产品为
8.680 秒。两者之差主要来自 SQLite 状态行、溯源记录以及产品收尾。

## 吞吐

| 粒子数 | FLEXPART 核心 | Trajecta 等效核心 | FLEXPART 产品 | Trajecta 产品 |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 7,519 粒子/s | 21,486 粒子/s | 7,634 粒子/s | 4,556 粒子/s |
| 50,000 | 37,313 粒子/s | 34,029 粒子/s | 36,496 粒子/s | 5,760 粒子/s |

这里的吞吐只对应固定的一小时、六个输送步案例，不代表每个模式步或每行输出的速率。延长模拟会
增加输送步数，缩短输出间隔会增加产品行数，两种变化对核心和完整产品时间的影响不同。

## 从 10,000 扩展到 50,000 粒子

| 计时边界 | 50k / 10k 墙钟时间比 |
| --- | ---: |
| FLEXPART 核心 | 1.008 |
| FLEXPART 产品 | 1.046 |
| Trajecta 等效核心 | 3.157 |
| Trajecta 产品 | 3.955 |

FLEXPART 在这两个粒子数之间几乎保持平坦。本案例只有六个输送步，启动、气象准备和按步处理的
固定成本占据了较大比例。在当前主机上，把粒子数组从 10,000 增加到 50,000 对中位数影响较小。

Trajecta 的粒子数增加五倍后，等效核心增长 3.16 倍。批量气象查询和内存数值路径使增长低于
线性。完整产品增长 3.96 倍，因为 SQLite 状态行和溯源记录随粒子与输出事件增加。

这些比值只对应当前步数和输出频率。模拟更长时，固定启动成本所占比例会下降；输出更频繁时，
产品写入所占比例会提高。

## 峰值常驻内存

| 粒子数 | FLEXPART 核心 | FLEXPART 产品 | Trajecta 产品 |
| ---: | ---: | ---: | ---: |
| 10,000 | 354.0 MiB | 354.6 MiB | 84.0 MiB |
| 50,000 | 361.8 MiB | 368.5 MiB | 163.1 MiB |

数值为三次计时运行中进程峰值常驻内存的中位数。当前矩阵中，Trajecta 完整结果路径的峰值较低，并且
随粒子数增长更明显。实际运行配置仍需根据资料、区域、时长、读取器和并发任务设置内存预算；
队列以声明预算进行资源准入。

## 估算其他负载

不同研究更适合通过小型本地标定估算。保持目标资料系列和输出间隔，运行两个粒子数，并记录：

```text
trajecta result inspect RESULT
trajecta run report --result RESULT
```

比较运行器时间、输出行数、SQLite 大小、峰值常驻内存和输出事件数。长时段研究还应单独改变
模拟时长，从而分开“每个输送步的成本”和“每条已保存粒子状态的成本”。

[原始数据与图表](data.md)提供全部重复样本，以及墙钟时间、吞吐和内存图。
